# caged repo — agent guide

You are working on the **caged** source repo: a hardened, disposable podman
container that runs `pi` (and other coding agents) as a non-root user on a
read-only filesystem. Your job is to improve this repo — the image, the
compose stack, the seed config, the scripts, the docs.

Read [README.md](README.md) for the full picture; this file captures what the
README doesn't — the conventions and gotchas that govern how you work here.

## The seed is the source of truth for pi config

`seed/.pi/agent/` IS pi's live config home (`~/.pi` at runtime), bind-mounted
**both ways**. Anything you write there takes effect on the *next* container
start — no image rebuild, no seed step. Concretely:

- To change providers/models: edit `seed/.pi/agent/models.json`.
- To add/change agent skills: edit **`seed/.pi/agent/skills.json`** (declarations)
  or **`seed/.pi/agent/skills-src/`** (your own skills). Never edit the
  generated copies in `seed/.pi/agent/skills/` — they carry a hidden
  `.caged-skill-managed` marker and are regenerated by `scripts/skills-sync.mjs`.
- To change the environment primer pi loads at startup: edit
  `seed/.pi/agent/AGENTS.md`.

There are therefore **two** AGENTS.md files in this repo, for two different
agents. Don't conflate them:

| File | Consumer | Purpose |
|---|---|---|
| `seed/.pi/agent/AGENTS.md` | pi *inside* the container | the runtime environment primer |
| **this file** (`/workspace/AGENTS.md`) | you, working *on* the repo | how to build/cage/iterate |

## Secrets never live in the repo

Provider keys (`$MY_DEEPSEEK_API_KEY`, `$VOLCENGINE_API_KEY`,
`$MY_OPENROUTER_API_KEY`, `$LOCAL_API_KEY`) and `GITLAB_TOKEN` are passed as
container env vars by the operator. They are referenced by name in
`models.json` / `compose.yaml` and expanded at runtime. Never write a real key
into `/workspace` — anything there is readable by the agent you're caging.
If a key is missing, tell the user which env var to set; don't fabricate one.

## Leading invariants (the load-bearing rules)

- **Non-root, no escalation.** The container runs as uid 1000 with
  `--cap-drop ALL`, `--no-new-privileges`, read-only rootfs. Don't add a
  `sudo` path or a privilege loophole — that dissolves the whole point.
- **Open network is deliberate.** Not a sandbox to add; document trade-offs in
  `docs/SECURITY.md` instead of trying to lock egress.
- **Fail-fast seed validation.** `scripts/entrypoint.sh` validates the seed
  mount (missing/incomplete seed, bad `mcp.json` executable, read-only seed)
  and exits non-zero with a diagnostic rather than letting pi run
  half-configured. Preserve that property when you touch the entrypoint.
- **Runtime state stays out of git.** `seed/.pi/agent/auth.json`,
  `seed/.pi/agent/sessions/`, `seed/.pi/agent/acli/` are gitignored. Sessions
  are per-project on the host (`$CAGED_WORKSPACE/sessions`), not in the seed.

## Working here

- Tools: `glab` for GitLab CLI, `acli` for Atlassian/Jira, `podman compose`
  for the stack. Prefer them over raw curl. Their auth/persistence behavior
  and trade-offs: `docs/CLI-AUTH.md`.
- The single runtime entry is `compose.yaml`. Prefer `run` over `up` for
  interactive TUI (podman-compose `up` doesn't forward terminal size/TERM).
- Skills can be synced by hand with `node scripts/skills-sync.mjs`
  (`--dry-run` to preview, `--link-only` / `--clone-only` for the split paths).
- After changing any seed config, the change is only visible on the next
  container start — call that out in your summary so the user knows when to look.
