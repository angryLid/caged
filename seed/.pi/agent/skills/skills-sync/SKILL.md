# skills-sync

Synchronises the skills declared in the project's `skills.json` into the
location pi scans for skills.

## Where skills live

This project is a container image ("caged") that runs pi. pi scans
`~/.pi/agent/skills/`, and `~/.pi` is a **live bind mount** of the host
`seed/.pi` dir (set up by compose.yaml). So the sync installs skills **into
the seed** — `seed/.pi/agent/skills/` — not into the project working tree.

Inside the seed:
- each source repo is cloned into `seed/.pi/agent/skills-sync/vendor/skills/<name>`
- each enabled skill is a **relative symlink** in `seed/.pi/agent/skills/`
  pointing back into that vendor dir (e.g. `glab ->
  ../skills-sync/vendor/skills/gitlab-ai-skills/skills/glab`)

Keeping the repos inside the seed keeps the relative links valid inside the
container's mount layout (everything lives under `/agent-home/.pi/agent`).

## How the sync runs

The entrypoint (`scripts/entrypoint.sh`) runs it at **every container start**
as a best-effort step, passing `--seed /agent-home/.pi/agent` (the live seed
mount). You can also run it by hand — e.g. right after editing `skills.json`:

```bash
node scripts/skills-sync.mjs              # do it (default seed: seed/.pi/agent)
node scripts/skills-sync.mjs --dry-run    # preview without changing anything
node scripts/skills-sync.mjs --seed /agent-home/.pi/agent   # explicit seed dir
```

Exit codes: `0` ok, `1` fatal, `2` warnings only (missing skill / collision) — links still applied.

## When the user edits `skills.json`

- Adding a skill to an existing repo's `enabled` → just re-run the script.
- Adding a whole new repo → the script clones it on the next run.
- Removing a skill → the script unlinks its symlink on the next run.

## Notes / gotchas

- **`seed/.pi/agent/skills-sync/vendor/` and the generated symlinks are
  gitignored** and regenerated by this script — don't commit them, don't edit
  symlinks by hand. Hand-written skills committed in `seed/.pi/agent/skills/`
  (bgm-metadata, caged-persistence, create-post, markdown-link, mdx-notes,
  skills-sync) are preserved.
- **Collisions**: two repos can ship a skill with the same name (e.g. `handoff`
  exists in both gitlab-ai-skills and mattpocock-skills). pi keeps the first
  one loaded and warns. Enable only one of a colliding pair.
- **Relative symlinks** are used on purpose so nothing is hardcoded to an
  absolute path — the links survive the project being cloned/mounted elsewhere.
- Repos are plain clones (not submodules) — the declarative config `skills.json`
  is the source of truth, and a fresh clone self-heals by re-cloning.
